# Treasure Hunt: operating and capacity notes

## Design

Camera frames, compass heading, the camera overlay, object projection and distance guidance run on the member's phone. The phone uses the joined hunt's current target coordinates and its own position and orientation to place one Treehouse coin or treasure in the camera picture. Its apparent size changes with distance, and it gently floats and turns. Only the start, next unclaimed checkpoint or final treasure is shown; other players are never part of this view. The camera is never uploaded, and no location is sent while the member walks. High-accuracy location watching runs only while the camera or compass view is open, smooths normal sensor wobble and ignores implausible jumps. It stops when the view closes or the app goes into the background. Animation and camera capture are limited to 30 frames per second. The hunt pauses when GPS reports travel above about 25 km/h.

The object is pinned by GPS and true-north compass maths, not by image recognition or surface/occlusion tracking. Its screen position and size are therefore approximate and can drift with GPS or compass quality. When accuracy is worse than 30 m, no item is placed; when a reliable true-north heading is unavailable, the app hides the camera direction arrow and says to use Google Maps. A radar view is available if the camera fails and inside the iPhone app. Google Maps walking directions open from either view and Maps handles its blue route and turn prompts. The first time the player opens the hunt view, a one-time reminder says to look up, watch the road and never play while driving.

At join, one location reading is sent only when the hunt has alternate starts or final treasure locations; the database assigns each the nearest option and does not save the reading. Tapping an item requests one fresh location fix and calls the existing start, checkpoint or final claim function. The database checks distance and idempotency, awards the coins and returns the new total; if it rejects the distance, the server's message appears and the item stays visible. No reward is ever created by the phone.

The member app calls Supabase RPCs through `lib/api.ts`. A screen visit loads the active hunt list once (kept in a 60-second in-memory cache per open app), joining assigns the nearest start and finish points and loads the route, and a start/checkpoint/final check-in sends one request. There is no hunt polling or new live channel. Leaderboard pages are fetched only when opened or when the member asks for another page; they are not cached because their visibility changes with hunt state. While a hunt has not ended, the RPC returns only the caller's rank, coins and total player count; after `ends_at` or when staff marks the hunt completed, it returns the paginated named leaderboard. The active-hunt list returns counts and only a yes/no indicator for route assignment; route coordinates are returned only to a member who joins. Each hunt has at most 10 start and 10 finish points, so nearest-point selection compares a bounded set.

Checkpoint and finish RPCs lock the participant row and enforce one award per checkpoint and one completion bonus. Claims accept a client request ID for safe retries and allow at most 10 attempts per participant per minute. Final leaderboards use keyset pagination, cap pages at 50, and expose a handle and game score, not account IDs or profile details. During a hunt, other participants' handles, progress and completion times are never returned. Private tables have RLS enabled and direct member access revoked. Staff changes are recorded in the existing audit log.

Admins manage the same hunt records in **admin.treehouse.ng → Grow → Treasure Hunts** and in **treehouse.ng → Profile → Product Announcements → Treasure Hunt setup**. The setup screen accepts Google Maps links that contain coordinates or a coordinate pair; it opens Maps to help staff inspect the public place and never loads a map API or transfers member location. A short Maps share link may omit coordinates, in which case staff copy the displayed pin coordinates. Coin and treasure designs use a fixed emoji picker. New hunts require at least one start, at least one final treasure location, and one shared checkpoint. After anyone joins, route details are locked; staff can cancel the hunt. In the Treehouse app, only Hydra's super-admin account can manage hunts without an authenticator code; the admin website and all other staff actions remain MFA-protected.

## Capacity model (estimates, not measured results)

Assumptions: a 90-minute hunt, five checkpoints, one catalogue open and join/resume, one start check-in, one final claim, and leaderboard use by a minority of participants. A typical active player is expected to make about **0.09–0.16 Treasure Hunt API requests per minute** averaged across the hunt. The average includes the first screen and later checkpoint actions; during a short launch burst, requests will be higher. A successful checkpoint RPC is one transaction with about 9 SQL statements (eligibility, participant lock, duplicate checks, rate counter, hunt/checkpoint reads, claim insert and progress update); error/retry paths are shorter. Across the mixed event, use about 5–10 DB statements per RPC as a rough estimate. A catalogue RPC performs a bounded set of hunt/checkpoint/participant lookups. A leaderboard page reads at most 51 ordered rows from its board index and joins profile handles.

| Concurrent players | Estimated steady Hunt requests | Estimated steady DB statements* | Estimated Hunt bandwidth** |
|---:|---:|---:|---:|
| 100 | 9–16/min (0.15–0.27/sec) | about 0.75–2.7/sec | about 0.01–0.06 Mbit/sec |
| 1,000 | 90–160/min (1.5–2.7/sec) | about 7.5–27/sec | about 0.1–0.6 Mbit/sec |
| 10,000 | 900–1,600/min (15–27/sec) | about 75–270/sec | about 1–6 Mbit/sec |

\*Statement estimates multiply the request rate by approximately 5–10 statements per RPC. They exclude unrelated Treehouse activity and should be replaced with observed database query counts. \**Assumes 10–30 KB round-trip per RPC with text/JSON responses, no map tiles or image uploads. Google Maps opens on the phone; its map tiles and route data are outside Treehouse bandwidth. Mobile radio/protocol overhead and initial app assets are excluded.

The normal server workload is small JSON and indexed database work; camera rendering and route math consume the member's device CPU and memory. At 10,000 concurrent participants, this model gives roughly 75–270 DB statements/second; database connection capacity, transaction wait time, database CPU, and overlap with chat/authentication are the main unknowns. There is no test result yet: this repository has no safe staging database or load-test credentials, and the live database must not be used for this test. These estimates are not a promise that the current infrastructure supports 10,000 concurrent players.

## Safe capacity test and scaling signals

Before opening a large event, run a staged load test against a separate approved test environment with seeded hunts and accounts. Ramp 100 → 500 → 1,000 → 2,500 → 5,000 → 10,000 simulated participants. Mix catalogue opens, joins, one checkpoint every 15–20 minutes, occasional leaderboard first/next pages, and finish calls. Include a launch burst (at least 10× steady request rate for two minutes). Do not send real camera footage or member location histories. Record p50/p95/p99 RPC latency, RPC errors/timeouts, database CPU, memory, active connections, slow queries, lock waits, cache hit rates, and traffic in/out. Run a parallel Treehouse baseline and verify authentication, chat, private messages, Discover, Games and notifications stay within their normal latency/error range.

Recommended pause/escalation thresholds for the test: pause the ramp if database CPU remains above 70% for five minutes, active connections exceed 70% of the configured limit, Hunt RPC p95 exceeds 500 ms or errors exceed 1% for five minutes, or any core Treehouse service's p95 rises more than 20% above its matched baseline. Keep existing capacity until measurement shows a bottleneck. First tune query plans, indexes and event size; only then recommend an approved capacity or workload-isolation change.

Monitor and alert on Hunt RPC request count and rate-limit rejections, error rate and p95/p99 latency; database CPU, memory, connections, slow queries and lock waits; and core app authentication/chat/Discover/Games/notification latency and errors. Set alerts against the site's established service objectives where available. No server, paid service or live database change is part of this feature.
