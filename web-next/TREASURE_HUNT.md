# Treasure Hunt: operating and capacity notes

## Design

Camera frames, compass heading, the camera overlay, object projection and distance guidance run on the member's phone. The phone uses the joined hunt's current target coordinates and its own position and orientation to place one Treehouse coin or treasure in the camera picture. Its apparent size changes with distance, and it gently floats and turns. Only the start, next unclaimed checkpoint or final treasure is shown; other players are never part of this view. The camera is never uploaded, and no location is sent while the member walks. High-accuracy location watching runs only while the camera or compass view is open, smooths normal sensor wobble and ignores implausible jumps. It stops when the view closes or the app goes into the background. Animation and camera capture are limited to 30 frames per second. The hunt pauses when GPS reports travel above about 25 km/h.

The object is pinned by GPS and true-north compass maths, not by image recognition or surface/occlusion tracking. Its screen position and size are therefore approximate and can drift with GPS or compass quality. When accuracy is worse than 30 m, no item is placed; when a reliable true-north heading is unavailable, the app hides the camera direction arrow and says to use Google Maps. A radar view is available if the camera fails and inside the iPhone app. Google Maps walking directions open from either view and Maps handles its blue route and turn prompts. The first time the player opens the hunt view, a one-time reminder says to look up, watch the road and never play while driving.

Joining sends one accurate location reading. The database picks the closest checkpoint as that player's starting point; it never saves the reading, and the grand prize cannot be a starting point. Each player starts with a private route containing every checkpoint exactly once. When they collect their starting checkpoint, the database builds a nearby-first route and spreads players who began at the same checkpoint across different next stops when it can do so without making the route more than about 30% longer. The route is fixed after that. Once the player has visited every checkpoint, the database assigns the grand-prize location closest to their last checkpoint. Tapping a target requests one fresh location fix and calls the existing claim function. The database checks distance and retry safety, awards the coins and returns the next target in that same response; if it rejects the distance, its message appears and the item stays visible. No reward is ever created by the phone.

Players who joined before this change keep their existing starting location and numbered route.

The member app calls Supabase RPCs through `lib/api.ts`. A screen visit loads the active hunt list once (kept in a 60-second in-memory cache per open app). Joining sends one location reading and receives only that player's current target; a checkpoint claim returns the next target with its result, so the phone does not need another request to advance. There is no hunt polling or new live channel. Leaderboard pages are fetched only when opened or when the member asks for another page; they are not cached because their visibility changes with hunt state. While a hunt has not ended, the RPC returns only the caller's rank, coins and total player count; after `ends_at` or when staff marks the hunt completed, it returns the paginated named leaderboard. The active-hunt list returns counts and joined status, never checkpoint locations. A player receives only their starting checkpoint or next checkpoint, then only their selected final treasure after all checkpoints are collected. The admin screen lets staff maintain checkpoint locations and up to 10 grand-prize choices; new hunts do not need separate start points.

Checkpoint and finish RPCs lock the participant row and enforce one award per checkpoint and one completion bonus. Claims accept a client request ID for safe retries and allow at most 10 attempts per participant per minute. Final leaderboards use keyset pagination, cap pages at 50, and expose a handle and game score, not account IDs or profile details. During a hunt, other participants' handles, progress and completion times are never returned. Private tables have RLS enabled and direct member access revoked. Staff changes are recorded in the existing audit log.

Admins manage the same hunt records in **admin.treehouse.ng → Grow → Treasure Hunts** and in **treehouse.ng → Profile → Product Announcements → Treasure Hunt setup**. The setup screen accepts Google Maps links that contain coordinates or a coordinate pair; it opens Maps to help staff inspect the public place and never loads a map API or transfers member location. A short Maps share link may omit coordinates, in which case staff copy the displayed pin coordinates. Coin and treasure designs use a fixed emoji picker. New hunts require at least one checkpoint and one final treasure location; the nearest checkpoint becomes each player's start. After anyone joins, route details are locked; staff can cancel the hunt. In the Treehouse app, only Hydra's super-admin account can manage hunts without an authenticator code; the admin website and all other staff actions remain MFA-protected.

## Capacity model (estimates, not measured results)

Assumptions: a 90-minute hunt, five checkpoints, one catalogue open and join/resume, one start check-in, one final claim, and leaderboard use by a minority of participants. A typical active player is expected to make about **0.09–0.16 Treasure Hunt API requests per minute** averaged across the hunt. The average includes the first screen and later checkpoint actions; during a short launch burst, requests will be higher. A checkpoint claim is one transaction with roughly 8–12 SQL statements for validation, duplicate checks, rate limits, distance verification, the reward update and compact progress response. The starting-checkpoint claim also builds the private route; for a five-checkpoint hunt, its route-building loop adds roughly 15 SQL statements overall, with several indexed reads each time it considers the next stop. Across the mixed event, budget about 8–15 DB statements per RPC as a code-based estimate, not a measurement. A catalogue RPC performs a bounded set of hunt/checkpoint/participant lookups. A leaderboard page reads at most 51 ordered rows from its board index and joins profile handles.

| Concurrent players | Estimated steady Hunt requests | Estimated steady DB statements* | Estimated Hunt bandwidth** |
|---:|---:|---:|---:|
| 100 | 9–16/min (0.15–0.27/sec) | about 1.2–4/sec | about 0.01–0.06 Mbit/sec |
| 1,000 | 90–160/min (1.5–2.7/sec) | about 12–41/sec | about 0.1–0.6 Mbit/sec |
| 10,000 | 900–1,600/min (15–27/sec) | about 120–405/sec | about 1–6 Mbit/sec |

\*Statement estimates multiply the request rate by approximately 8–15 statements per RPC, including one route assignment per player. They exclude unrelated Treehouse activity and should be replaced with observed database query counts. \**Assumes 10–30 KB round-trip per RPC with text/JSON responses, no map tiles or image uploads. Google Maps opens on the phone; its map tiles and route data are outside Treehouse bandwidth. Mobile radio/protocol overhead and initial app assets are excluded.

The normal server workload is small JSON and indexed database work; camera rendering and live navigation math consume the member's device CPU and memory. Route construction runs once per player at their starting checkpoint. It compares nearby stops and balances against earlier players from the same start; its work rises with checkpoint count, and its transaction briefly locks the hunt row so simultaneous players are assigned against up-to-date routes. At 10,000 concurrent participants, this model gives roughly 120–405 DB statements/second before launch bursts; database connection capacity, transaction wait time, database CPU, and overlap with chat/authentication are the main unknowns. There is no test result yet: this repository has no safe staging database or load-test credentials, and the live database must not be used for this test. These estimates are not a promise that the current infrastructure supports 10,000 concurrent players.

## Safe capacity test and scaling signals

Before opening a large event, run a staged load test against a separate approved test environment with seeded hunts and accounts. Ramp 100 → 500 → 1,000 → 2,500 → 5,000 → 10,000 simulated participants. Mix catalogue opens, joins, one checkpoint every 15–20 minutes, occasional leaderboard first/next pages, and finish calls. Include a launch burst (at least 10× steady request rate for two minutes). Do not send real camera footage or member location histories. Record p50/p95/p99 RPC latency, RPC errors/timeouts, database CPU, memory, active connections, slow queries, lock waits, cache hit rates, and traffic in/out. Run a parallel Treehouse baseline and verify authentication, chat, private messages, Discover, Games and notifications stay within their normal latency/error range.

Recommended pause/escalation thresholds for the test: pause the ramp if database CPU remains above 70% for five minutes, active connections exceed 70% of the configured limit, Hunt RPC p95 exceeds 500 ms or errors exceed 1% for five minutes, or any core Treehouse service's p95 rises more than 20% above its matched baseline. Keep existing capacity until measurement shows a bottleneck. First tune query plans, indexes and event size; only then recommend an approved capacity or workload-isolation change.

Monitor and alert on Hunt RPC request count and rate-limit rejections, error rate and p95/p99 latency; database CPU, memory, connections, slow queries and lock waits; and core app authentication/chat/Discover/Games/notification latency and errors. Set alerts against the site's established service objectives where available. No server, paid service or live database change is part of this feature.
