# Treasure Hunt: operating and capacity notes

## Design

Camera frames, compass heading, the camera overlay, item projection and route-point projection run on the member's phone. The phone uses the joined hunt's current target and its own position and orientation to place one Treehouse coin or treasure in the camera picture. Its apparent size changes with distance, and it gently floats and turns. Only the start, next unclaimed checkpoint or final treasure is shown; other players are never part of this view. The camera is never uploaded. High-accuracy location watching runs only while the camera or compass view is open, smooths normal sensor wobble and ignores implausible jumps. It stops when the view closes or the app goes into the background. Camera capture and animation are limited to 30 frames per second. There is no speed-based pause; before first use, players confirm: “Passengers only: never play while driving. Watch out for traffic.”

The item is pinned by GPS and true-north compass maths, not by image recognition or surface/occlusion tracking. Its screen position and size are approximate and can drift with sensor quality. When accuracy is worse than 30 m, no collectible is placed; route arrows fade while the turn banner and Google Maps option remain. When a reliable true-north heading is unavailable, the app hides the camera direction arrow and says to use Google Maps. A compass/radar view is available if the camera fails and inside the iPhone app. On the web and Android app, the member app requests a Google Routes walking route through `/api/hunt-route`; the travel switch can request driving directions for a passenger in a bus or car. Teal ground arrows are projected from route points on the phone, and the next instruction, remaining distance and time appear in the banner. The item appears at the target when the player is within about 60 m; tapping still calls the existing database claim with a fresh position, and the database alone awards coins. If route guidance is unavailable, the existing direction arrow and Google Maps link remain available.

The route endpoint sends Google only the current origin, the current target and the travel mode. It sends no hunt or checkpoint names, member IDs, handles, camera frames or location history, and it does not log coordinates. Route requests happen once when a target changes and again only after the player is more than 40 m off the route or taps Recenter. There is no location polling to the server. Signed-in members are verified through Supabase Auth; each member is limited to one route request every 20 seconds and 60 per hour. Identical route requests can be reused from a short 30-second in-process cache. The cache holds at most 120 recent routes and route lines are capped at 2,000 points. This cache and limit use each Railway app process's memory; Google Cloud API quotas are the shared cap if Railway runs more than one process.

To enable road guidance, Hydra creates a Google Cloud project, enables the Routes API, creates an API key restricted to the Routes API, sets usage quotas and billing alerts, then adds the key to the existing Railway member-app service as `GOOGLE_ROUTES_KEY`. The key stays server-side and must not be placed in a `NEXT_PUBLIC_*` variable or committed. No map tiles or extra server are needed. If no key is configured, or Google is unavailable, the app falls back to the existing direction arrow and Maps link. The Routes API may incur Google Maps Platform charges; check the current Google Cloud pricing and quota settings before enabling it.

Joining sends one accurate location reading. The database picks the closest checkpoint as that player's starting point; it never saves the reading, and the grand prize cannot be a starting point. Each player starts with a private route containing every checkpoint exactly once. When they collect their starting checkpoint, the database builds a nearby-first route and spreads players who began at the same checkpoint across different next stops when it can do so without making the route more than about 30% longer. The route is fixed after that. Once the player has visited every checkpoint, the database assigns the grand-prize location closest to their last checkpoint. Tapping a target requests one fresh location fix and calls the existing claim function. The database checks distance and retry safety, awards the coins and returns the next target in that same response; if it rejects the distance, its message appears and the item stays visible. No reward is ever created by the phone.

Players who joined before this change keep their existing starting location and numbered route.

The member app calls Supabase RPCs through `lib/api.ts`. A screen visit loads the active hunt list once (kept in a 60-second in-memory cache per open app). Joining sends one location reading and receives only that player's current target; a checkpoint claim returns the next target with its result, so the phone does not need another request to advance. There is no hunt polling or new live channel. Leaderboard pages are fetched only when opened or when the member asks for another page; they are not cached because their visibility changes with hunt state. While a hunt has not ended, the RPC returns only the caller's rank, coins and total player count; after `ends_at` or when staff marks the hunt completed, it returns the paginated named leaderboard. The active-hunt list returns counts and joined status, never checkpoint locations. A player receives only their starting checkpoint or next checkpoint, then only their selected final treasure after all checkpoints are collected. The admin screen lets staff maintain checkpoint locations and up to 10 grand-prize choices; new hunts do not need separate start points.

Checkpoint and finish RPCs lock the participant row and enforce one award per checkpoint and one completion bonus. Claims accept a client request ID for safe retries and allow at most 10 attempts per participant per minute. Final leaderboards use keyset pagination, cap pages at 50, and expose a handle and game score, not account IDs or profile details. During a hunt, other participants' handles, progress and completion times are never returned. Private tables have RLS enabled and direct member access revoked. Staff changes are recorded in the existing audit log.

Admins manage the same hunt records in **admin.treehouse.ng → Grow → Treasure Hunts** and in **treehouse.ng → Profile → Product Announcements → Treasure Hunt setup**. The setup screen accepts Google Maps links that contain coordinates or a coordinate pair; it opens Maps to help staff inspect the public place and never loads a map API or transfers member location. A short Maps share link may omit coordinates, in which case staff copy the displayed pin coordinates. Coin and treasure designs use a fixed emoji picker. New hunts require at least one checkpoint and one final treasure location; the nearest checkpoint becomes each player's start. After anyone joins, route details are locked; staff can cancel the hunt. In the Treehouse app, only Hydra's super-admin account can manage hunts without an authenticator code; the admin website and all other staff actions remain MFA-protected.

## Capacity model (estimates, not measured results)

Assumptions: a 90-minute hunt, five checkpoint locations (including the starting point), one catalogue open and join/resume, one claim per checkpoint, one final claim, and leaderboard use by a minority of participants. A typical active player is expected to make about **0.16–0.24 Treehouse Hunt API requests per minute** averaged across the hunt. This includes roughly six initial Google route requests (one for each checkpoint target and one for the final treasure) over 90 minutes, plus the existing app/database requests; add one route request per detour that needs a reroute. That is roughly 1.2–1.8 Google route calls per player per 20 minutes on average. A checkpoint claim is one transaction with roughly 8–12 SQL statements for validation, duplicate checks, rate limits, distance verification, the reward update and compact progress response. The starting-checkpoint claim also builds the private route; for a five-checkpoint hunt, its route-building loop adds roughly 15 SQL statements overall, with several indexed reads each time it considers the next stop. Across database RPCs, budget about 8–15 SQL statements per RPC as a code-based estimate, not a measurement. A catalogue RPC performs a bounded set of hunt/checkpoint/participant lookups. A leaderboard page reads at most 51 ordered rows from its board index and joins profile handles. Each Google route request also causes one signed-in member verification through Supabase Auth; these Auth checks are outside the Postgres RPC statement estimate.

| Concurrent players | Estimated steady Hunt requests | Estimated steady DB statements* | Estimated Hunt bandwidth** |
|---:|---:|---:|---:|
| 100 | 16–24/min (0.27–0.40/sec) | about 1.2–4/sec | about 0.03–0.12 Mbit/sec |
| 1,000 | 160–240/min (2.7–4/sec) | about 12–41/sec | about 0.3–1.2 Mbit/sec |
| 10,000 | 1,600–2,400/min (27–40/sec) | about 120–405/sec | about 3–12 Mbit/sec |

\*Statement estimates apply only to database RPCs and multiply the existing 0.09–0.16 RPC/player/minute by approximately 8–15 statements. They include one route assignment per player, exclude the separate Supabase Auth identity checks for route calls and unrelated Treehouse activity, and should be replaced with observed query counts. \**Assumes 10–30 KB per existing app RPC and 10–60 KB for each compact route response; no map tiles or image uploads. Google Maps opens on the phone; its map tiles are outside Treehouse bandwidth. Mobile radio/protocol overhead and initial app assets are excluded.

The normal server workload is small JSON, a short Supabase Auth check and one outbound Google Routes request when a target changes or a reroute is needed; camera rendering and live route projection consume the member's device CPU and memory. The route proxy keeps at most 120 compact routes in process memory for 30 seconds. Route construction in the database runs once per player at their starting checkpoint. It compares nearby stops and balances against earlier players from the same start; its work rises with checkpoint count, and its transaction briefly locks the hunt row so simultaneous players are assigned against up-to-date routes. At 10,000 concurrent participants, this model gives roughly 120–405 DB statements/second plus about 11 Supabase Auth route checks/second at steady average traffic before launch bursts; database connection capacity, transaction wait time, database CPU, Auth latency, and overlap with chat/authentication are the main unknowns. There is no test result yet: this repository has no safe staging database or load-test credentials, and the live database must not be used for this test. These estimates are not a promise that the current infrastructure supports 10,000 concurrent players.

## Safe capacity test and scaling signals

Before opening a large event, run a staged load test against a separate approved test environment with seeded hunts and accounts. Ramp 100 → 500 → 1,000 → 2,500 → 5,000 → 10,000 simulated participants. Mix catalogue opens, joins, one checkpoint every 15–20 minutes, occasional leaderboard first/next pages, and finish calls. Include a launch burst (at least 10× steady request rate for two minutes). Do not send real camera footage or member location histories. Record p50/p95/p99 RPC latency, RPC errors/timeouts, database CPU, memory, active connections, slow queries, lock waits, cache hit rates, and traffic in/out. Run a parallel Treehouse baseline and verify authentication, chat, private messages, Discover, Games and notifications stay within their normal latency/error range.

Recommended pause/escalation thresholds for the test: pause the ramp if database CPU remains above 70% for five minutes, active connections exceed 70% of the configured limit, Hunt RPC p95 exceeds 500 ms or errors exceed 1% for five minutes, or any core Treehouse service's p95 rises more than 20% above its matched baseline. Keep existing capacity until measurement shows a bottleneck. First tune query plans, indexes and event size; only then recommend an approved capacity or workload-isolation change.

Monitor and alert on Hunt RPC request count and rate-limit rejections, error rate and p95/p99 latency; `/api/hunt-route` status and latency; Google Routes API request count, quota and billing; Supabase Auth latency; database CPU, memory, connections, slow queries and lock waits; and core app authentication/chat/Discover/Games/notification latency and errors. Alert before Google usage reaches 70% of its configured quota, if route/API errors exceed 1% for five minutes, if route p95 exceeds two seconds for five minutes, or if any core Treehouse service rises more than 20% above its matched baseline. Never include coordinates or member identifiers in route logs. Set alerts against the site's established service objectives where available. No server, paid service or live database change is part of this feature.
